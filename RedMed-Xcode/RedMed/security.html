Security practices for the RedMed iPhone app, passerby card page, and passive NFC medical bracelet used in the United States

In Short RedMed is local-first: no operator backend for your profile, no accounts, no cloud sync of medical fields. On-device storage uses the iOS Keychain. The NFC band is deliberately plaintext so any phone can open the emergency card — same trade-off as a printed medical ID. RedMed is not a HIPAA covered entity or business associate for that profile.

This page describes how RedMed approaches security for the App, the hosted passerby card, and the bracelet. It is informational, not a warranty. Read it with the Privacy Policy and Terms Of Service.

1. Threat Model

Security work focuses on (1) keeping your profile off RedMed servers, (2) protecting on-device storage, (3) hosted page integrity for the passerby card, and (4) safe rendering of untrusted #d= payloads. We do not attempt to make a passive NFC medical ID confidential against a deliberate close tap — that would defeat the product.

2. HIPAA Context

HIPAA regulates covered entities and their business associates when they handle protected health information. RedMed does not receive your RedMed profile on our systems and is not a covered entity or business associate for that profile. Device-local Keychain encryption and the absence of a profile backend reduce exposure; they are not a substitute for a covered entity’s HIPAA Security Rule program, and we do not market the band as “HIPAA certified.”

3. On-Device Profile Storage

  • Profile fields persist in the iOS Keychain with WhenUnlockedThisDeviceOnly.
  • Readable only while the device is unlocked; excluded from iCloud and encrypted device backups.
  • Face ID / Touch ID / device passcode gates edit and NFC write flows where implemented.
  • Clearing fields and saving overwrites the stored profile; deleting the App removes the Keychain entry.

4. NFC Band (Deliberately Unencrypted)

Passive NFC medical payloads are plaintext (#d= base64url JSON) so any smartphone can open the emergency card without an account. Cloning a tag is like photocopying a wallet medical card. Casual walk-by distance will not fire the band; only a deliberate ~1–2″ antenna tap reads it. Payment / POS terminals use a different protocol (EMV) and do not open the RedMed card.

5. Location

GPS starts only on Find Help (When-In-Use). Coordinates stay on-device for display to you / a dispatcher. We do not receive, log, or retain them. Do not log location.hash, NFC URLs, profile JSON, or PIN material in any tooling you add later.

6. Reporting Vulnerabilities

Open a private GitHub security advisory on RedmMed/RedMed for vulnerabilities in the hosted card page or XSS in #d= rendering. Do not file public issues with live API keys or real medical payloads.

7. Trust Root (Cloudflare Pages)

Every band tap opens the Cloudflare Pages deploy of card/, pushed by GitHub Actions on every merge to main. Treat main as production:

  1. Enable branch protection on main (required PR reviews, no force-push).
  2. Restrict who can edit the deploy workflow and repository secrets — CLOUDFLARE_API_TOKEN grants Pages deploy access.
  3. Actions are pinned to commit SHAs (not mutable tags) in the deploy workflow.

8. Google Maps API Key

9. Dependencies

Almost no runtime deps (no npm, no CocoaPods). Do not add analytics or crash SDKs that phone home profile or location without an explicit product decision — that would change both the privacy posture and, if PHI were ever transmitted to a vendor under a covered-entity arrangement, the HIPAA analysis.
